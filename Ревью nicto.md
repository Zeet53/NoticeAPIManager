### Общие замечания
1. Codestyle
	- Наименования методов свойств классов различаются. Рекомендация от Майков - PascalCase. Например, sendData -> SendData
	- Рекомендуется классы объявлять в отдельных файлах. Есть исключения, например, авто-генерированный код. Для малых проектов - не критично.
2. Использование статических классов-сервисов
	- Рекомендуется избегать статические классы. Сложнее тестировать, сложнее реализовать масштабирование. Вместо них используются не статические классы с регистрацией в DI-контейнере как Singleton. Для "заглушек" не критично.
3. Преобразование DTO
	- Для преобразования моделей рекомендуется использовать методы расширения или мапперы (иногда explicit-операторы). Для небольших проектов не критично
4. Взаимодействие с CacheService.
	- Обращение к CacheService через REST API, скорее всего, снизит производительность. Рекомендовал бы обращаться к redis непосредственно по месту, где необходимо кеширование. CacheService реализовать в виде класса-сервиса. Для повторного использования, его можно вынести в nuget-библиотеку.
5. Зависимости от реализации
	- При использовании классов, реализующих сервисный функционал возникает зависимость от реализации. Таким образом нарушается принцип инверсии управления (IoC). Рекомендуется использовать интерфейсы при проектировании классов-сервисов, а взаимодействие осуществлять через интерфейсы. Принцип применяется для уменьшения связности между компонентами. В частности, проще реализовать различное поведение при изменении требований или настроек. Упрощается разработка модульных тестов.
